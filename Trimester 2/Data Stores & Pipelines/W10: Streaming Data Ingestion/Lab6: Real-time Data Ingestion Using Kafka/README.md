# Lab6: Real-time Data Ingestion Using Kafka

Lab 6: Real-time Data Ingestion Using Kafka:

This hands-on lab covers the foundational implementation of real-time data ingestion using Apache Kafka. Learners configure an Apache Kafka cluster, manage topics and partitions, build programmatic producers to publish serialized event streams, implement consumer groups to scale message consumption, and handle partition offset commits to guarantee reliable delivery.

Lab Objectives:

- Start a local Apache Kafka cluster and verify broker operational status.
- Create, inspect, and configure multi-partition Kafka topics using command-line administrative scripts.
- Develop a Python producer script to serialize and stream structured JSON event records into Kafka topics.
- Develop a Python consumer application to retrieve messages continuously using the consumer poll loop.
- Scale multiple consumer instances within a single consumer group and observe dynamic partition assignment.
- Implement manual offset commits to prevent silent message loss and observe at-least-once delivery behavior.
- Monitor consumer lag across partitions using command-line diagnostic tools.

Step 1: Environment Setup and Cluster Initialization:

- Start the cluster coordination service, using either KRaft mode or ZooKeeper, depending on the Kafka installation version.
- Launch the Kafka broker process and confirm the broker is listening on standard ports, typically port 9092.
- Verify cluster availability by inspecting broker startup logs for the successful controller registration message.

Step 2: Topic Creation and Partition Configuration:

- Execute the kafka-topics utility to create an ingestion topic, such as user-events.
- Specify the bootstrap server address to connect to the active broker.
- Configure the topic with four partitions to allow concurrent consumption by multiple consumer instances.
- Set the replication factor to one for local single-node test environments.
- Run the describe command to review the topic configuration, confirming partition IDs and leader assignments.

Step 3: Baseline Command-Line Testing:

- Use the kafka-console-producer tool in a terminal window to enter manual text messages and confirm connectivity.
- Open a second terminal window running the kafka-console-consumer tool to verify that messages typed into the producer appear instantly in the consumer output.
- Pass the from-beginning argument to confirm that earlier messages persisted in the partition log can be read historically.

Step 4: Python Producer Implementation:

- Install the kafka-python or confluent-kafka client library into the Python virtual environment.
- Instantiate a KafkaProducer object with bootstrap servers configured to the local broker address.
- Provide a value serializer lambda function that converts Python dictionaries into UTF-8 encoded JSON byte streams.
- Define a key serializer to encode string identifiers into raw bytes for partition routing.
- Implement a loop generating synthetic user events, including user identifier, action type, session ID, and UTC timestamp.
- Assign the user identifier as the message key to ensure that all events generated by a single user are routed to the same partition.
- Use asynchronous message delivery with callback functions to track successful partition offsets and capture connection errors.

Step 5: Python Consumer Implementation:

- Instantiate a KafkaConsumer object subscribed to the user-events topic.
- Define the group.id configuration property to assign the consumer to an identifiable consumer group.
- Configure a value deserializer that parses raw incoming byte arrays back into native Python dictionaries.
- Set the auto.offset.reset property to earliest so that new consumers read from the beginning of the partition log if no prior offset is found.
- Implement an infinite poll loop to fetch message batches from the broker, unpack payload fields, and simulate data processing.

Step 6: Offset Management and Delivery Semantics:

- Disable automatic offset commits by setting enable.auto.commit to false in consumer configuration.
- Process the fetched batch of records completely before issuing an offset commit.
- Call the commitSync method immediately after successful message processing to store the latest processed offset in the internal Kafka consumer offsets topic.
- Simulate a process crash by halting the consumer script mid-execution, restart the consumer, and confirm that processing resumes from the last successfully committed offset.
- Important: Committing offsets manually only after the consumer finishes processing prevents unhandled exceptions from dropping records silently.

Step 7: Consumer Group Scaling and Lag Monitoring:

- Launch two separate terminal windows running instances of the Python consumer script configured with the exact same group.id.
- Observe that Kafka rebalances the topic, assigning two partitions to the first consumer instance and two partitions to the second instance.
- Launch two additional consumer instances with the same group ID so that all four partitions have an exclusive consumer.
- Launch a fifth consumer instance and verify that it remains in an idle standby state because the consumer count exceeds the partition count.
- Execute the kafka-consumer-groups tool with the describe flag to inspect partition log-end offsets, current consumer offsets, and total consumer lag for the group.

Troubleshooting Common Issues:

- Connection refused errors indicate that the broker is offline, the port is blocked, or the advertised.listeners configuration property is misconfigured.
- Serialization errors occur when complex non-primitive data types, such as raw datetime objects, are passed to the JSON encoder without string conversion.
- Rebalance storms occur when message processing inside the poll loop takes longer than max.poll.interval.ms, causing the cluster coordinator to assume the consumer has died.

Key Takeaways:

- Apache Kafka decouples event producers from consumers, acting as a high-throughput, partitioned append-only log.
- Topic partitions establish the unit of parallelism and determine the maximum number of active consumers in a consumer group.
- Assigning consistent message keys ensures sequential ordering for records belonging to the same entity.
- Manual offset commits provide reliable at-least-once processing guarantees and prevent data loss during application crashes.
- Consumer lag is the most critical operational metric for determining whether consumers are processing events quickly enough to avoid backlog accumulation.
