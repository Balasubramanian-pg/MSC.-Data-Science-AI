# W10: Streaming Data Ingestion

Streaming Data Ingestion:

Streaming data ingestion is the practice of capturing, transporting, and loading continuous event streams generated by operational systems, mobile applications, financial transactions, and telemetry devices. Unlike batch architectures that process bounded historical files at fixed intervals, streaming architectures process unbounded data in near real time. This week covers the fundamental mechanics, storage brokers, ingestion patterns, delivery guarantees, and architectural designs used to build resilient streaming systems.

Core Concepts of Streaming Data:

- Unbounded datasets: Data has no fixed beginning or end, arriving continuously as independent event payloads.
- Event structure: An event typically contains a key identifying the entity, a payload containing state change information, and a timestamp recording when the action occurred.
- Stream producers: Client applications, microservices, database change logs, and internet of things sensors that emit messages into ingestion buffers.
- Message brokers: Distributed append-only commit logs that decouple event producers from downstream consumers and provide durable message buffering.
- Consumer groups: Pools of subscriber applications that read records cooperatively from message brokers, dividing partitions to scale throughput.

Distributed Message Broker Architectures:

- Apache Kafka: A distributed event log organized into topics, partitions, and broker nodes. Partitions provide horizontal scalability and establish total order of messages within a single partition.
- Partitioning keys: Kafka uses the hash of a message key to assign records to specific partitions, ensuring that events for the same entity are processed in chronological order.
- Offset management: Consumers maintain an integer pointer called an offset that marks their progress within a partition log, allowing them to pause, resume, or replay streams after failures.
- AWS Kinesis and Azure Event Hubs: Managed cloud streaming alternatives that provide partitioned stream ingestion without requiring cluster management.
- Google Cloud Pub/Sub: An enterprise messaging service that abstracts partition management in favor of automatic horizontal scaling and dynamic consumer balancing.

Delivery Guarantees and Processing Semantics:

- At-most-once delivery: Messages are delivered once without retries. This approach ensures zero duplicate processing, but network blips or application crashes can cause message loss.
- At-least-once delivery: Messages are resent until acknowledged by the consumer. This ensures that no records are lost, but network retries can introduce duplicate records that downstream systems must handle.
- Exactly-once processing: Guarantees that each message impacts final state calculations exactly once. Achieving this requires end-to-end coordination, including transactional message writes, state checkpointing, and idempotent consumers.
